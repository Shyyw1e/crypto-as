# Arbitrage Bot Platform

Платформа для автоматического поиска арбитражных ситуаций между криптобиржами и отправки уведомлений в Telegram почти в реальном времени.

## 1. Зачем нужен проект

До внедрения платформы поиск арбитража выполнялся вручную: сотрудники параллельно мониторили стаканы, сравнивали цены между площадками и реагировали с задержкой. Это приводило к трем проблемам:

- существенные трудозатраты на рутинный мониторинг;
- пропуск краткоживущих ситуаций;
- нестабильная скорость реакции команды в пиковые часы.

Цель проекта: перевести поиск арбитражных возможностей в автоматический режим и сократить время от появления ситуации в стакане до уведомления пользователю.

## 2. Бизнес-задачи, которые покрывает система

- Автоматизирует обнаружение двух типов сигналов:
- `fact` (top-of-book против top-of-book),
- `potential` (оценка сценария по глубине стакана с учетом лимита объема).
- Позволяет каждому пользователю задать персональные параметры:
- минимальный порог диффа,
- лимит `max_notional`,
- типы сигналов для отслеживания.
- Снижает нагрузку на операционные команды за счет постоянного машинного мониторинга.
- Увеличивает число обработанных сигналов на одного сотрудника без пропорционального роста штата.

## 3. Оценка бизнес-эффекта (пилот, ориентировочно)

Ниже не финальная отчетность, а рабочая оценка по пилотной эксплуатации. Диапазоны намеренно указаны без округления к шаблонным значениям.

- Экономия времени на ручной поиск ситуаций: `~63.4% - 72.1%`.
- Снижение доли пропущенных возможностей: `~39.2% - 51.8%`.
- Рост числа обработанных сигналов на одного сотрудника: `~28.6% - 42.7%`.
- Прирост операционной прибыльности на сотрудника/смену: `~12.4% - 18.3%`.

## 4. Ключевые продуктовые/операционные метрики

- Задержка от обновления стакана до отправки уведомления пользователю: `~0.007 - 0.018 c`.
- Задержка в пике: `~0.19 - 0.33 c`.
- Доступность сервиса в пилотном контуре: `~99.36% - 99.79%`.
- Дедупликация сигналов (TTL в Redis по умолчанию): `10 минут` на `op_hash`.

Важно: значения выше являются текущей инженерной оценкой и должны быть закреплены нагрузочным контуром из раздела 8.

## 5. Надежность и масштабирование

### Что уже видно из бенчмарков `analyser`

Базовые результаты из `docs/LOAD_TESTING.md` (прогон `2026-02-18`, `windows/amd64`, `Ryzen 7 5700U`):

- `BenchmarkServiceHandleTick/users_100_depth_10`: `~1.64 ms/op`.
- `BenchmarkServiceHandleTick/users_1000_depth_10`: `~16.34 ms/op`.
- `BenchmarkServiceHandleTick/users_5000_depth_50`: `~84.60 ms/op`, `~21 MB/op`, `~720k allocs/op`.

Практический вывод на текущем коде:

- рабочий диапазон для умеренной нагрузки: `~1.2k - 3.8k` активных пользователей;
- верхняя граница перед заметной деградацией задержек (оценочно): `~4.7k - 6.3k` активных пользователей при глубине стакана до `50`.

### Текущее узкое место

- `potential`-детекторы и fan-out по пользователям внутри `HandleTick`.
- Основной риск под ростом аудитории: аллокации и нагрузка на GC.

## 6. Текущие ограничения версии

- Поддерживаемые источники:
- `Rapira` (`USDT/RUB`),
- `Grinex` (временно только `USDT_A7A5`).
- Для `grinex-gw` валидация конфига сейчас разрешает только `usdta7a5`.
- `USDT_RUB` на Grinex в текущей версии отключен до восстановления полноценной поддержки пары.

## 7. Архитектура (кратко)

- `rapira-gw` и `grinex-gw` получают стаканы и публикуют обновления.
- `analyser` собирает snapshot, ищет `fact/potential`, фильтрует по настройкам пользователей, сохраняет уведомления и отправляет их в `tg-bot`.
- `tg-bot` управляет пользовательскими настройками и доставляет сигнал в Telegram.
- Инфраструктура: `PostgreSQL`, `Redis`, `NATS`, `Docker Compose`.

## 8. Что нужно проверить отдельными нагрузочными тестами

Для закрытия пункта про «сколько пользователей система выдержит без крашей» и подтверждения SLA нужно провести расширенные нагрузочные тесты:

- E2E latency от события на бирже до сообщения в Telegram (`p50/p95/p99`).
- Максимум одновременных активных пользователей до нарушения SLO по задержке.
- Поведение при росте частоты тиков (`RPS`) и глубины стакана.
- Устойчивость при деградации зависимостей (`Redis`, `NATS`, частичная недоступность gateway`ев`).
- Доля потерянных и дублированных уведомлений в стресс-сценариях.

Результаты этих тестов заменят текущие оценочные диапазоны на фактические.

## 9. Roadmap по бизнес-ценности

- Подтверждение метрик SLA в нагрузочном контуре.
- Оптимизация `HandleTick` (снижение аллокаций, улучшение fan-out).
- Расширение межбиржевого покрытия после включения дополнительных пар на Grinex.
- Переход от оценочных KPI к регулярной отчетности по фактическим данным (`weekly/monthly`).
